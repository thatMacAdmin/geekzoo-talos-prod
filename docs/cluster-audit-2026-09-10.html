01Stop credentials entering ingress access logsAuthorization and Cookie headers are written verbatim by Traefik. Restrict header logging before reviewing historical exposure.P1+
SecurityIngress / observabilitySmall configuration change; historical review

Evidence level: Verified with synthetic request

Observed evidence

  • All three Traefik pods run --accesslog.fields.headers.defaultmode=keep.
  • A harmless GET to the website through the origin returned HTTP 200. Its access-log JSON contained the exact synthetic Bearer value and synthetic Cookie value sent by the audit. No real credentials were used or reproduced.
  • Source: infrastructure/controllers/traefik/helm-values.yaml:84–97. Access logs go to stdout (line 116).

Why it matters

Any credentials carried in these headers can be copied into the logging trust boundary. A user or process with log access may gain access beyond the intended application. Historical real-token exposure and downstream retention were not enumerated.

Work to tackle

  1. Use a default-deny header logging policy; allow only operationally necessary, non-sensitive headers. Explicitly drop Authorization, Cookie, Set-Cookie and application API-key headers.
  2. Identify where Traefik logs are shipped, who can query them and how long they are retained. Treat historic logs as potentially sensitive; restrict access immediately and assess session/token rotation.
  3. Do not bulk-delete audit evidence or log storage without an agreed retention/incident-handling decision.

Definition of done

Repeat the synthetic request through every Traefik replica. Keep HTTP status, latency and route metadata, but confirm no credential/header values appear in stdout or the central log store.

Rollout guardrail

Deploy through the Traefik Helm values in Git. If diagnostics are lost, add specific safe fields; do not restore keep-all header logging.

02Remove Grafana’s cluster-wide Secret read accessGrafana provisioning has more Kubernetes authority than dashboard discovery requires.P1+
SecurityObservability / platform securitySmall–medium; provisioning regression checks

Evidence level: Verified live RBAC and sidecar configuration

Observed evidence

  • ClusterRole kube-prometheus-stack-grafana-clusterrole grants get, list and watch on configmaps and secrets; its ClusterRoleBinding attaches it to the Grafana service account.
  • The dashboard sidecar uses RESOURCE=both and NAMESPACE=ALL. The datasource sidecar also uses RESOURCE=both. The Grafana application container mounts the same service-account token.
  • Configuration owner: observability/kube-prometheus-stack/helm-values.yaml:134 onward; there is no narrow sidecar/RBAC override in the inspected Grafana block.

Why it matters

Compromise of Grafana or a component sharing its token could expose Secrets from other namespaces. Dashboard labels limit what a sidecar selects, not what Kubernetes RBAC authorizes.

Work to tackle

  1. Inventory dashboard and datasource provisioning inputs. Prefer ConfigMaps for non-secret dashboards and scope discovery to the namespaces actually needed.

  3. Stop mounting the provisioning service-account token in the main Grafana container if it does not need Kubernetes API access; use an explicit sidecar token mount or separate provisioning workload.

Definition of done

The Grafana identity cannot list Secrets across namespaces; expected dashboards/datasources still provision and reload. Check the rendered RBAC, not just sidecar environment variables.

Rollout guardrail

Retain a provisioning inventory and previous chart values. Restore only the minimum namespace/resource access necessary to recover a failed datasource reload.

03Establish and prove non-database backup coverageThe documented Velero recovery path is not installed. PostgreSQL backup health does not cover mail, application files or NAS data.P1+
RecoveryStorage / application ownersMedium; inventory and isolated restore drill

Evidence level: Velero absent; external backup coverage unknown

Observed evidence

  • The API server has no backups.velero.io, schedules.velero.io or backupstoragelocations.velero.io resource types, and the pod inventory contains no Velero controller or node agent.
  • The repository declares a velero namespace but no tracked Velero installation or schedule. Several workloads explicitly exclude their media mounts from Velero capture.
  • Positive control: all eight CNPG scheduled backups created on 10 September completed successfully, between 00:00:02 and 00:05:46 UTC; all eight clusters report ContinuousArchivingSuccess.
  • No independent TrueNAS backup policy, off-cluster PVC recovery evidence or recent application restore drill was verified.

Why it matters

A recoverable PostgreSQL database is not a recoverable application when its attachments, mail, configuration or other files are missing. Ceph replication protects against selected failures; it is not an independent backup. Absent Velero does not prove external backups do not exist.

Work to tackle

  1. Create a coverage matrix for the 49 PVCs and external NFS datasets, starting with Stalwart mail data, Vaultwarden attachments and irreplaceable app configuration. Record the real backup system, destination, retention, encryption and owner.
  2. Either restore a GitOps-managed volume backup path or document and verify an existing independent mechanism. Verify object/data movement off the source storage; local snapshots alone are insufficient for cluster loss.
  3. Perform an isolated CNPG point-in-time recovery plus representative file/PVC restores. Record application checks, achieved recovery point and recovery time. Keep bootstrap access to AWS, Wasabi and decryption material recoverable outside the cluster.

Definition of done

Every irreplaceable dataset has a current successful independent backup and a recorded restore result. Missing backup alerts detect a disabled schedule as well as a failed job.

Rollout guardrail

Restore only to isolated names/volumes. Never overwrite production PVCs during a drill. Keep existing backup copies and retention unchanged until the replacement is proven.

04Give AdGuard’s nearly full volume headroomapps/adguard-pvc is 92.9% used, despite ample free capacity in Ceph.P1+
PerformanceDNS / storageSmall; retention check and controlled expansion

Evidence level: Verified live volume metrics

Observed evidence

  • Kubelet reports 9,751,363,584 bytes used and 724,267,008 bytes available: approximately 9.08 GiB used and 691 MiB available. The filesystem capacity is approximately 9.77 GiB.
  • PVC request and live capacity are 10Gi. StorageClass ceph-block has allowVolumeExpansion=true.
  • Source: apps/adguard/pvc.yaml:7–12. No volume-filling alert was firing in the sampled Prometheus alert inventory. This does not establish that alert rules are missing.

Why it matters

Exhausting an application filesystem can break database writes, query logging or configuration changes, potentially affecting DNS service. Free capacity in the Ceph pool does not automatically enlarge this filesystem. Time to exhaustion was not forecast.

Work to tackle

  1. Inspect AdGuard’s query-log/statistics retention and directory sizes without exposing query contents. Identify whether growth is expected or a retention failure.
  2. After confirming backup coverage, choose a larger PVC size based on retention and growth, and increase the request in Git. Do not delete state blindly.
  3. Add or tune a sustained low-free-space alert for this critical volume; verify delivery and its interaction with existing predictive alerts.

Definition of done

PVC and mounted filesystem both show the intended new size, adequate free-space margin and successful DNS reads/configuration writes. A controlled alert test reaches the operator.

Rollout guardrail

PVC expansion is not reversible by shrinking the request. Treat the size increase as one-way; retention changes should be independently reversible.

05Close unauthenticated Traefik management accessThe Traefik API is accessible at the origin without authentication on both HTTPS and the management entrypoint.P1+
SecurityIngress / network securitySmall–medium; verify both origin paths

Evidence level: Verified unauthenticated origin responses

Observed evidence

  • Unauthenticated GET /api/overview returned HTTP 200 via the service on port 443 with Host traefik.macbytes.io and via port 8080. Requests used a local Kubernetes port-forward; response bodies were not collected.
  • Service traefik/traefik exposes port 8080 as well as 80/443 and advertises both an IPv4 VIP and a global IPv6 VIP.
  • The dashboard HTTPS IngressRoute targets api@internal without authentication middleware on /api and /dashboard. Its root redirect is not an authentication control.

Why it matters

Any principal able to reach these origin paths can read management/API information. Internet reachability was not tested: router/firewall and Cloudflare Access policies may add controls, but they do not constitute verified origin protection.

Work to tackle

  1. Remove the management entrypoint from the externally exposed Service unless explicitly required.

Definition of done

Unauthenticated origin requests cannot read /api or /dashboard; authorized operators can access them. Confirm port 8080 is no longer externally exposed and keep a documented break-glass path.

Rollout guardrail

Use temporary authenticated port-forward access if an operator is locked out; do not reopen the management LoadBalancer port as the default rollback.

06Remove full privilege from the torrent applicationThe qBittorrent container runs privileged as root; the VPN sidecar is also fully privileged.P1+
SecurityMedia / platform securityMedium; image and VPN compatibility checks

Evidence level: Verified live securityContext and source

Observed evidence

  • Live qBittorrent securityContext: privileged=true, runAsUser=0, runAsGroup=0, allowPrivilegeEscalation=true. Source: media/qbittorrent/deployment.yaml:157–167.
  • Gluetun has privileged=true plus NET_ADMIN and a /dev/net/tun hostPath mount (source lines 48–51, 107–116).
  • The effective Talos Pod Security default is enforce=baseline, with warn/audit=restricted; privileged namespaces are further exceptions. The repository’s operating guidance claiming a restricted cluster default is inaccurate.

Why it matters

An application that processes untrusted torrent traffic has a substantially weaker container boundary than necessary. VPN networking requirements should not grant the torrent application full privilege. PUID/PGID environment variables are not equivalent to a restricted pod securityContext.

Work to tackle

  1. Remove privileged mode from qBittorrent first. Validate the image’s initialization/ownership requirements and use the least capabilities and UID model it actually supports.
  2. Reduce Gluetun to its documented networking/device requirements rather than full privilege, preserving the VPN kill switch and leak prevention. Validate runtime compatibility before rollout.
  3. Stage restricted enforcement for ordinary application namespaces after reviewing warnings; isolate unavoidable privileged workloads. Correct the operating documentation to match effective admission policy. Disable unnecessary application service-account token mounts.

Definition of done

Downloads, Web UI, ownership and volume writes work without privileged qBittorrent. VPN-disconnect tests fail closed, DNS does not leak, and unrelated restricted workloads still schedule.

Rollout guardrail

Roll out one container/security boundary at a time. Keep the previous image/config available, but treat any temporary privilege exception as explicit and time-bounded.

SecurityCilium / application ownersMedium; dependency mapping and staged policies

Evidence level: Verified policy inventory; no packet-level isolation test

Observed evidence

  • Five NetworkPolicies exist: four in flux-system and one named redis in database. There are zero CiliumNetworkPolicies and zero CiliumClusterwideNetworkPolicies.

09Investigate observed OOM kills before changing limitsJellyfin and a Ceph manager have recorded OOM kills; node memory trends do not show sustained pressure.P2+
PerformanceMedia / Ceph operationsMedium; correlate the actual failure windows

Evidence level: Verified termination reasons and historical metrics

Observed evidence

  • Jellyfin’s last termination was OOMKilled (exit 137), 5 September at 10:12:50 UTC. It has a 4Gi limit and 2Gi request; the seven-day restart metric increased once.
  • rook-ceph-mgr-b last terminated OOMKilled on 28 August at 01:46:49 UTC with a 1Gi manager limit. Its 14-day sampled peak working set was approximately 1,022 MiB.
  • Seven-day node memory-use p95 is only 24.7–35.2%. Sampled Jellyfin p95 memory is much lower than its limit; scrape intervals can miss short-lived peaks or child-process usage.
  • OOMKilled establishes the termination reason, not by itself whether the trigger was a container limit or host-wide pressure. A follow-up kernel-log request to node-03 timed out; that distinction remains unverified.

Why it matters

OOM kills interrupt streaming or manager availability. A container limit can cause a kill even when the host has free RAM; this is a hypothesis to validate, not a confirmed cause for both events. A standby manager limits impact but does not resolve the underlying memory issue.

Work to tackle

  1. Correlate Jellyfin’s failure with transcodes, scans, plug-ins and child processes. Inspect container-level memory/oom counters, not only application RSS.
  2. Check Ceph manager module memory trends and release-specific fixes; retain manager failover.
  3. Adjust requests/limits only after identifying the working-set envelope and burst allowance. Preserve node recovery headroom; do not blindly increase every limit or restart the cluster.

Definition of done

The previously implicated workload scenario completes without OOM; memory has explicit headroom and restart alerts fire. Review longer-term trends for leaks after the change.

Rollout guardrail

Keep workload and limit changes separate. Revert a problematic image/module change independently; avoid lowering limits while the live working set exceeds them.

10Make image updates reproducible and risk-awareMediaManager uses latest with IfNotPresent; automated image changes also promote directly to the production branch.P2+

Evidence level: Verified source; GitHub protection settings not inspected

Observed evidence

  • media/mediamanager/deployment.yaml uses quay.io/maxdorninger/mediamanager:latest with IfNotPresent, without a matching image-automation policy in the inspected repository.

11Define failover expectations for intentional single pointsFour databases and the sole cloudflared connector have single-instance availability limits.P2+
RecoveryPlatform / service ownersMedium; architecture decision and controlled drill

Evidence level: Live topology verified; outage tolerance is a decision

Observed evidence

  • Live CNPG clusters artifactsctl, inbox-zero, mediamanager and vikunja each have 1/1 instance. Authentik, bifrost, seerr and vaultwarden have 3/3.
  • The cloudflared deployment intentionally runs one replica to preserve a 25 Mbit/s per-pod egress ceiling. It recorded two restarts in the seven-day metric window; the latest error termination was 9 September at 07:55:09 UTC.
  • All three nodes are also control-plane/storage nodes. The operator reports both 25G links per node share one switch; six interfaces report 25 Gbit/s. Switch resilience and bond failover were not exercised.

Why it matters

Backups do not provide immediate service continuity. A single database pod may recover only after rescheduling and volume attachment; a single connector interrupts remote access during replacement. Dual links on one switch do not eliminate the switch failure domain.

Work to tackle

  1. Agree service-specific RPO/RTO and maintenance tolerance before increasing replicas. Promote the most critical single-instance databases to host-separated replicas where the benefit justifies it.
  2. Review cloudflared termination logs and separate liveness from upstream readiness semantics; do not assume the recorded restarts had the same cause.
  3. If redundant connectors are required, redesign the aggregate bandwidth control first. Do not simply scale to two and double the intended uplink allowance.
  4. Run one controlled node/link maintenance scenario after recovery coverage is proven, with rollback access and no concurrent Ceph maintenance.

Definition of done

Measured failover/recovery times meet the agreed service budget. A connector rollout preserves the aggregate cap; DNS, mail, databases and storage recover without manual surprises.

Rollout guardrail

Schedule disruptive drills explicitly. Preserve the existing single-connector cap until a replacement is validated; retain replicas until database scale-down is safely reviewed.

A safe delivery sequence

  1. Contain credential and management exposure

    Fix access-log headers, scope Grafana RBAC and protect both dashboard origin paths. Limit access to historical logs while exposure is assessed. Keep a tested operator access path.

  2. Protect recoverability and the next likely capacity failure

    Verify irreplaceable PVC/NAS coverage and perform isolated restores. Give AdGuard headroom. The Ceph warning gets its own expiry check around 17:01 UTC on 11 September; do not wait for a sprint to check that timestamp.

  3. Reduce privilege and lateral movement

    Harden qBittorrent and its VPN sidecar carefully, then stage namespace policy boundaries. Canary origin certificate verification one hostname at a time. Avoid coupling all security changes into one rollout.

  4. Make operations predictable

    Investigate OOM/restart scenarios, pin mutable images and agree release promotion rules. Decide recovery-time budgets before scaling databases or changing the deliberately capped tunnel topology.

All persistent cluster changes go through reviewed GitOps commits. Operator approval is required before pushing to the live source. Disruptive tests and irreversible changes need their own maintenance decision.

Controls worth preserving

  • Reconciliation is healthyAll 21 HelmReleases and 17 Flux Kustomizations reported Ready in the live snapshot.
  • Database backup jobs are succeedingEight latest scheduled CNPG backups completed; every cluster reported successful continuous WAL archiving. Restore usability still needs separate proof.
  • API-server protections are configuredAll three servers disable anonymous authentication and profiling, and configure audit logging plus an encryption provider. Encryption key contents and stored ciphertext were not inspected.
  • Admission is not absentTalos enforces baseline by default and warns/audits restricted, with kube-system exempt. Strengthen it deliberately rather than assuming namespace-label absence means no protection.
  • Identity and secret delivery existFlux uses the GitHub provider. Application credentials use External Secrets; Grafana has Authentik OAuth with TLS verification enabled in its configuration.
  • Storage is not degradedCeph monitors have quorum, all OSDs are up/in and all PGs are clean. The health warning must remain visible until its event window expires or recurrence is investigated.

Scope, evidence & limitations

What was checked

  • Live nodes, pods, resources, PVCs, RBAC, namespace and network policies, admission configuration, ingress/services and safe configuration projections.
  • Prometheus node/container/storage trends and active alerts. Ceph health, latency and drive evidence from the preceding investigation.
  • CNPG Backup and ScheduledBackup status, archiver conditions, Velero API/pod presence, Flux reconciliation and targeted repository manifests.
  • Harmless HTTP GETs at a local port-forwarded origin. Synthetic non-secret headers proved logging behavior; unauthenticated dashboard responses proved origin behavior.

What this does not establish

  • No penetration test, complete CIS benchmark, image/CVE scan, dependency scan or packet-level policy test.
  • No Cloudflare account/Access/WAF, GitHub branch-protection, AWS IAM, Wasabi immutability, TrueNAS backup or upstream IPv4/IPv6 firewall audit.
  • No restore, node drain, disk benchmark, switch/bond failover or application load test.
  • No exhaustive manifest schema/build validation or complete Git-history secret scan. Current target-file review is not proof that the repository has never contained a secret.
  • No application outage or compromise inferred solely from a configuration risk. Missing recovery evidence is explicitly not proof that no external backup exists.
